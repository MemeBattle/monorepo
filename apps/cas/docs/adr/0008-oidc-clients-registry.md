# 8. OIDC clients registry

## Status

Accepted (2026-09-20), with [#740](https://github.com/MemeBattle/monorepo/issues/740).

## Context

CAS is about to become an OpenID Provider: `/authorize` (#742) will hand an
authorization code to an application, `/token` (#743) will exchange it, and a
guest grant (#746) will mint a guest for an application that is allowed one.
Every one of those endpoints has to answer the same questions first — is this
a client CAS knows, is it the client it claims to be, may the response be
sent where it asks, may it ask for these scopes — and none of them can answer
without a registry.

`docs/PLAN.md` already settled the shape of the answer: "statically
registered clients (DB, managed by hand until the admin panel)". What is left
is what a client row holds, what identifies it, what the store keeps of a
secret, how loosely a redirect URI may be matched, and how a row gets in at
all when there is no admin panel and no Dynamic Client Registration (M5) to
put it there.

The open questions are not evenly weighted. Redirect URI matching is the one
that decides whether the authorization code can be stolen; the rest are
questions of shape. So it is settled here, once, rather than left to each
endpoint.

## Decision

**(a) `clients` belongs to a `clients` context, keyed by the OIDC
`client_id`.** The table is `id text PRIMARY KEY` — the `client_id` itself, a
slug an operator picks (`ligretto`), not a generated uuid with the name
beside it. Operators, configuration files, the sibling tickets and the
protocol all address a client by that name, and a second identifier would
only be a thing to keep in step. The shape is enforced by the domain rather
than by a CHECK: `[a-z0-9._-]`, at most 64 characters. The id travels in
query strings, `Basic` credentials, configuration and logs, and a narrow
character set is what keeps two clients from looking alike there. `kind` is a
Postgres enum (`client_kind`: `public`, `confidential`), like `account_type`
before it. `created_at` is the database's; there is no `updated_at`, because
nothing updates a row yet.

**(b) A confidential client's secret is generated by CAS, shown once, and
stored only as its SHA-256.** `ClientSecret::generate` draws 32 random bytes
and renders them base64url; `cas-client` prints the value once on stdout and
the table keeps `secret_hash bytea`, compared in constant time
(`subtle::ConstantTimeEq`) because the comparison runs on every `/token` call
against a value the caller controls. A slow password hash (argon2, bcrypt) is
deliberately not used: it exists to make a low-entropy human choice expensive
to guess, and there is no human choice here — the binary has no `--secret`
flag, so 256 bits of machine entropy is the only thing that can be in the
column. The same reasoning already governs session tokens (ADR 0004) and will
govern refresh tokens. A KDF on the token path would cost every exchange and
buy nothing.

The invariant that a secret belongs to exactly the confidential clients is
held in two places, because both can be reached independently: a CHECK
constraint, `clients_secret_hash_matches_kind`, ties `secret_hash IS NOT
NULL` to `kind = 'confidential'` for anything that writes the table, and
`NewClient::public` / `NewClient::confidential` make the other combinations
unrepresentable in Rust. A public client has no hash, and `verify_secret` is
`false` for it — there is nothing a caller could present that would be right.

**(c) Redirect URIs are matched by exact string comparison.** `Client::
allows_redirect_uri` is true only when a registered value equals the
candidate byte for byte: no prefix match, no wildcard host, no case folding,
no tolerated trailing slash, no loopback port variance (RFC 8252 §7.3), no
custom URI schemes. Each of those relaxations is a known way to turn an
authorization code into someone else's; none of the planned clients needs
one. The same rule covers the post-logout redirect URI (#745), which is the
same open-redirect surface with a different name.

Exact matching decides how a URI is *stored*: as it was typed, untouched.
That in turn decides what registration must refuse, and this is subtler than
it looks. The `url` crate implements the WHATWG parser, which is a repair
shop — it strips tabs and newlines, trims surrounding controls and spaces,
percent-encodes stray characters, rewrites a backslash as a slash and reads
`https:app.example` as `https://app.example`. A successful parse therefore
proves nothing about the string that was typed, and a repaired value would be
stored in a form no real request could ever equal. So registration checks, in
order: every byte is an RFC 3986 URI character; the parse succeeds *and* the
parser reported no syntax violation; the scheme is `http` or `https`; there
is a host; there is no fragment (RFC 6749 §3.1.2). What it does not require
is that the parsed form equal the typed one — parsing adds a trailing slash
to a bare origin, and it is the typed form that is stored. The consequence is
that `https://app.example` and `https://app.example/` are two different
registrations. That is what exact matching means, and saying so here is
cheaper than discovering it at `/authorize`.

**(d) `scopes` is an allow-list, `first_party` and `guest_login_allowed` are
gates.** `scopes text[]` holds RFC 6749 scope tokens and defaults to
`{openid}`, without which a request is not an OpenID Connect request at all;
`/authorize` refuses a request for anything outside the list.
`first_party` means the client skips the consent screen — the applications in
this ecosystem are ours, and a consent dialog between a user and their own
game is friction, not information. `guest_login_allowed` gates the guest
grant (#746), which mints an account without any user interaction and so must
be something a client is granted rather than something it can ask for. The
`aud` (resource identifier) per client is not here: #743 adds that column
when the token endpoint needs it, rather than guessing its shape now.

**(e) Rows are written by the `cas-client` binary, not by a migration.** A
migration is immutable and runs in every environment, so seeding a `ligretto`
client with a known secret would put that secret in production — the one
thing (b) is designed to prevent. `cas-client register` is the documented
path instead; `scripts/seed-dev.sh` calls it to give a fresh development
database its `ligretto` client, with placeholder redirect URIs until ligretto
is wired to CAS ("Ligretto on CAS", M4 of the epic #548, which supersedes the
older milestone list in `docs/PLAN.md`). The script is not idempotent, and
that is the point: a second run fails with "already exists", which says the
client is there. The binary has one subcommand. Updating, listing, deleting
and rotating a secret belong to the admin panel (M6); until then a mistake is
fixed by registering another id or resetting the dev database. The use case
itself lives in the library (`clients::registration::register`), so the
binary stays what every binary here is — load the config, call into the
library, nothing else — and so a `#[sqlx::test]` can exercise the whole path
without starting a process.

**(f) The registry has no HTTP surface.** Nothing in `http/` changes and
`ApiState` gains nothing. `/authorize` and `/token` will read the registry
through `ClientRepository` (or a service over it) and own their own OAuth
error mapping, which is theirs to define: the same "no such client" is an
error page on one endpoint and an `invalid_client` JSON body on the other.

## Consequences

- #742, #743, #745 and #746 have their vocabulary: `Client::verify_secret`,
  `allows_redirect_uri`, `allows_post_logout_redirect_uri`, `allows_scope`,
  and a `ClientRepository::get` to reach them by id. None of them re-decides
  how strictly a redirect URI is compared.
- Every string the table holds is read back through a validated newtype, so a
  row written or altered outside CAS surfaces as a decode error instead of
  widening where an authorization response may be sent. That is the accounts
  rule (ADR 0006 (e)) applied to a table where the stakes are higher.
- `url` and `subtle` become direct dependencies of the crate. Both were
  already in `Cargo.lock` through `webauthn-rs`, so nothing new is
  downloaded; `url` is taken directly rather than through
  `webauthn_rs::prelude::Url` (as `config.rs` does), because a context has no
  business depending on the WebAuthn crate.
- The dev `ligretto` secret is different on every seeded database. Nothing
  consumes it yet. When ligretto needs a stable one, the binary can grow a
  dev-only `--secret` flag, and that decision is recorded then; not adding it
  now is what keeps the "never chosen by a person" property of (b) true.
- Registering a client is an operator action with a secret in its output, so
  `cas-client` writes the secret and nothing else to stdout: the log line,
  the usage text and every error go to stderr, and a script can capture the
  secret by reading stdout alone.
